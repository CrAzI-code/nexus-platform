# In-app notifications

NEXUS stores notifications in PostgreSQL and scopes every inbox query to the
authenticated recipient. Task, project, and organization notifications are
created in the same Prisma transaction as the business change, using a unique
recipient/event key to make retries safe. The API publishes newly committed
records over authenticated server-sent events; the dashboard refreshes its
unread count periodically and reloads persisted items when the inbox opens or
the stream reconnects.

The inbox covers task assignment, status changes, comments and name-based
mentions, blockers, due-date changes, overdue tasks, project membership, and
organization invitations. Invitation notifications are only visible for a
verified matching email address and a still-pending invitation. If an invite
was created before the recipient had a NEXUS account, the inbox creates its
deduplicated notification when the signed-in user next refreshes notifications.

Due-date changes notify the task creator and assignee other than the actor.
Overdue alerts are generated by an API lifecycle worker on startup and every
minute. It uses a PostgreSQL transaction-scoped advisory lock so only one API
instance scans at a time, row locks with `SKIP LOCKED`, and a due-date index.
The notification event key includes the task, current UTC due timestamp, and
recipient; the worker's `NOT EXISTS` check and the database uniqueness
constraint make retries and restarts safe. Completed/archived tasks and
inactive memberships are excluded. Changing a due date creates a new
deduplication generation if the new date is overdue. Due dates are date-only
UTC values; a task becomes overdue on the UTC day after its due date.

Project membership is managed directly by an organization/project manager
rather than through a separate project-invitation acceptance workflow. When
someone is added to a project, they receive a notification that links to that
project. Notification messages avoid comment bodies, invitation tokens, and
other private payloads. Revoked invitations and resources outside the
recipient's current organization/project access are filtered; if a task is no
longer available, its target API still enforces access and returns its normal
not-found response.

The SSE stream polls authorized persisted notifications in PostgreSQL and
uses millisecond-precision timestamp-plus-ID event cursors for reconnect replay.
The timestamp precision matches JavaScript `Date`, while UUID tie-breaking keeps
notifications created in the same millisecond in a stable order. Post-commit
publish signals wake connections on the same instance; polling recovers events
written by other instances and missed local signals. The notification table
remains the source of truth, so restarts do not lose delivery. No Redis or
external broker is required. Delivery latency for overdue alerts is up to one
minute; SSE catch-up polling runs every three seconds per open connection.
